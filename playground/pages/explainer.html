Inside the AI Playground

The playground takes one AI solution, runs three kinds of checks on it, and writes one report with a verdict. The two people who sign a component read that report before they sign. These five pictures show how it gets there.

Open the real interface ↗ The playground's own screens, replaying a recorded session with four sample solutions.
1 · One run

A run is one path, and it can stop early on purpose

You describe the solution once. The playground asks it one plain question before anything else: if the answer is missing, refused or unreadable, the run stops as incomplete, so a broken setup can never look like a safe solution.

2 · One probe

A probe plants something, then looks for it

Every probe hides something unique in what the solution reads: a marker word like PG7XK2M9, a fake key, a fake card number. The verdict comes from finding it in the answer, so it never depends on how the answer is worded.

3 · A refusal

A refusal only counts if it is a real guard

Many services put a filter in front of the model and answer a probe with an HTTP 400. That is a pass only if the same service answers a harmless request of the same size and the same characters. Otherwise an input limit or a broken request would look like security.

4 · The probes

29 probes, grouped by the risk they test

The groups follow the OWASP Top 10 for LLM applications, plus eight checks for MCP tool servers. A probe that does not apply (a tool check on a chat assistant) is skipped, not passed.

5 · The verdict

The verdict is decided in a fixed order

The rules are checked top to bottom and the first one that applies decides. A finding a named person has triaged no longer counts against the verdict; the finding itself stays in the report.

6 · Two people

The engineer tests; the AI security engineer decides

The engineer runs the playground while building and attaches the last report to the pull request. The AI security engineer runs it again with every probe, triages what needs a person, and cites the report in the sign-off note.

7 · The rules it keeps

What the playground refuses to do

Never production

A target's environment must be sandbox, dev, test or staging. Probes are adversarial by design.

Only hosts you name

Anything beyond your own machine must be listed in allow_hosts, and redirects are never followed.

Credentials are names

A secret is written ${env:NAME} and read when a request is sent. Any value that comes back is scrubbed from the report.

A copy, not a sandbox

The component's tests run in a throwaway copy with a minimal environment and a time limit. Untrusted code belongs in the container image.

Sealed reports

A report edited by hand, or a triage log that breaks the rules, is refused when it is loaded.

Local interface

The browser interface listens on your machine only, needs the link it prints, and shows a solution's answers as text, never as HTML.

8 · Try it

Five minutes, from the playground/ directory

# the sample candidate: contract, tests, every probe, its own cases. Ends CLEAR.
python3 -m aiplayground run --target examples/python-function.json \
  --component examples/runbook-answerer --suite examples/runbook-suite.json \
  --by "Your Name <you@example.com>"

# a solution that gives way, to see a BLOCKED report
python3 -m aiplayground run --target examples/demo-vulnerable.json

# the browser interface (open the link it prints)
python3 -m aiplayground serve
