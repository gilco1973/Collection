# Code review skill

## When to use
Any pull request that touches AI features, prompts, tool definitions, evaluation sets or
the gateway integration. Also any change where the author states that part of the code
was generated by a model.

## Inputs
- The diff and its description (Internal tier).
- The evaluation results attached to the pull request.

## Steps
1. Read the description, then the diff, then the tests. Note claims the diff does not support.
2. Check paved-road conformance: gateway used, classification header set, prompts in
   source control, evaluation present and not worse than main.
3. Check the [security checklist](../../best-practices/security.md): untrusted content
   delimited, tool gate present, outputs validated.
4. For AI-generated code, review as if written by a fast junior: look for plausible but
   untested branches, silent fallbacks, and swallowed exceptions.
5. Write findings ordered by severity with a concrete failure scenario for each.

## Tools
| Tool | Mutating | Notes |
| --- | --- | --- |
| Source-control read | No | Diff, history, CI status |
| Comment | Yes | Findings only; never approve or merge on behalf of a person |

## Checks before finishing
- [ ] Every finding has a scenario, not just an opinion.
- [ ] Evaluation delta stated explicitly.
- [ ] No finding quotes a secret or customer data.

## Output format
`Severity — file:line — scenario — suggested fix`, most severe first, then a one-line verdict.

## Evaluation
`evals/` — 8 diffs with expected findings, graded by finding overlap.
